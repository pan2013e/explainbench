You are designing a Python expression `<expr>` to be used as a multiple-choice distractor**.
The real correct expressions are the ones that change value before and after a code patch.
Your job is to generate one expression that resembles the correct ones if possible**, but that is actually incorrect because it does NOT change value.

### Inputs
You will be given:
- A Python function from a repository
- A specific line within that function
- State differences at that line before and after the patch
- Complete variable states before and after the patch
- A list of existing expressions that *do* change value (the correct answers)

### Task
Produce exactly one Python expression `<expr>` that:
1. Does NOT change its resulting value or exception behavior between “before” and “after” states.
2. If possible**, resembles the structure, style, or level of complexity of the existing changing expressions.
3. If resemblance is not reasonably achievable**, still produce a strong, non-trivial distractor that meets all constraints.
4. Is non-trivial (see structural constraints).
5. Is not an obvious tautology or constant.
6. Is not an obvious rewrite of any existing expression.

Your output must be only a valid Python expression**, with no explanation or added formatting.

### Hard Semantic Constraints
1. `<expr>` must evaluate to exactly the same result (same value or same exception behavior) in both states.
2. `<expr>` may reference only variables present in the variable states.
3. The final value must be a primitive (`None`, `int`, `float`, `str`, `bool`) or a built-in collection of primitives.
4. `<expr>` must not rely on any variable, attribute, or element whose value differs between states.

### Structural Constraints
1. `<expr>` MUST NOT be:
   - a bare variable,
   - a bare attribute or index access,
   - a single literal.
2. `<expr>` must use at least one of:
   - arithmetic operator (`+`, `-`, `*`, `/`, `//`, `%`, `**`)
   - comparison (`==`, `!=`, `<`, `<=`, `>`, `>=`)
   - logical operator (`and`, `or`, `not`)
   - aggregator/predicate (`len`, `sum`, `min`, `max`, `any`, `all`, `sorted`, comprehensions`)
3. `<expr>` should preferably mimic the complexity or pattern of the existing changing expressions—unless that is infeasible.
4. `<expr>` must not be a trivial identity, such as `x == x`, `len(lst) - len(lst)`, or any always-constant arithmetic.
5. `<expr>` must not be an obvious constant like `2 + 2` or `"a" == "a"`.

### Relationship to Existing Expressions
1. `<expr>` must NOT be identical to any existing expression.
2. Avoid trivial modifications:
   - simple negations,
   - adding/subtracting constants,
   - wrapping/casting,
   - reordering subexpressions.
3. The distractor should *feel* like a plausible candidate that could have changed—unless resemblance is not possible—while still being semantically stable.
