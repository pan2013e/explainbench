### Task
Produce exactly {n_output} Python expressions `<expr>` that:
1. have the same outcome between the buggy and patched programs:
   (a) yield the same values, or
   (b) yield the same program state between the buggy and patched programs (e.g., both are raising exceptions), and
2. have the same complexity as the correct expressions if possible, and
3. if resemblance is not reasonably achievable, still produce a strong, non-trivial distractor that meets all constraints. You are allowed to pick reasonable variable within the input function and generate a reasonable expression based on this variable

### General Rules
1. If `__return__` present; you can treat this as a special local variable that holds the value of the current function's return value. You can access it anytime.
2. Handling cases where return and exception differ between versions
If exactly one of the buggy or patched executions has a return value and the other has a exception (i.e., one version returns normally while the other raises an exception):
  - You must treat `__return__` as the seed for all generated expressions, regardless of which version produces it.
  - You are not allowed to reference `__exception__` in any generated expression.
  - All generated expressions must be derived from or composed using return and other permitted in-scope variables only.
3. If `__return__` does not exist and __exception__ is present in both the buggy and patched versions, treat `__exception__` as a restricted two-field, tuple-like value representing the exception raised by the current function. You may reference only:
  - `__exception__[0]`: the exception type as a string
  - `__exception__[1]`: the exception message as a string
4. The final value of `<expr>` must be a primitive (`None`, `int`, `float`, `str`, `bool`) or a built-in collection of primitives.
5. Follow `### Actions to Build the Expressions` to build more complex `<expr>`

### Actions to Build the Expressions
You may choose one or more of the following to build more complex expressions from the seed expression or other in-scope variables that differ between before and after.

1. Binary operations
  - arithmetic operators: `+`, `-`, `*`, `/`, `//`, `%`
  - comparison operators: `==`, `!=`, `<`, `<=`, `>`, `>=`
  - logical operators: `and`, `or`, `not`
  - identity/membership operators: `is`, `is not`, `in`, `not in`

2. Attribute access
   - Access attributes or methods of the variables:
     - `foo.bar`, `foo.bar()`
   - Only use attributes or methods that exist in the provided variable states.

3. Indexing and slicing
   - Index or slice sequences, mappings, or numpy arrays:
     - `foo[bar]`, `foo[0]`, `foo[-1]`, `foo[1:3]`

4. Wrapping with functions
   - Wrap the expression using:
     1. Python built-ins:
        `len`, `sum`, `min`, `max`, `any`, `all`, `sorted`, `tuple`, `list`, `dict`, `set`, `bool`, `str`, `int`, `float`, `abs`, `round`, `hash`, `type`, `isinstance`, `getattr`, `hasattr`, `enumerate`, `zip`
     2. NumPy functions (if `np` is available in the states):
        `np.allclose`, `np.array_equal`, `np.isnan`, `np.isclose`, etc.

5. Conditional expressions
   - Use Python’s ternary operator to build predicates that can flip between before and after:
     - `expr_if_true if condition else expr_if_false`

6. Combination with other changed variables
   - Identify variables whose values differ between before and after, and combine them with the generated expression that differs in value.

7. Collection-building expressions
   - Build small collections of primitives or expressions:
     - tuples, lists, sets, dicts

### Relationship to Existing Expressions
1. `<expr>` must NOT be identical to any existing expression.
2. Avoid trivial modifications:
   - simple negations,
   - adding/subtracting constants,
   - wrapping/casting,
   - reordering subexpressions.
3. The distractor should *feel* like a plausible candidate that could have changed—unless resemblance is not possible—while still being semantically stable.
