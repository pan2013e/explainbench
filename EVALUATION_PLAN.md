# ExplainBench Evaluation Plan

## Purpose

This document records the agreed design and implementation status for `explainbench evaluate`. It is the detailed companion to `PACKAGING_PLAN.md`.

The evaluator must support:

- Preset lite and full modes.
- Fine-grained selection of any supported question type.
- Shared benchmark-owned intent questions.
- Model-specific effect questions produced by a question builder.
- A temporary workflow that stages existing effect artifacts until question-builder functionality is implemented.

## Core artifact ownership decision

Intent and effect artifacts have different owners and lifecycles.

### Intent artifacts are owned by ExplainBench

Intent questions are provided by the benchmark and are identical for every submitted model. Their filenames therefore do not contain a submission or agent suffix:

```text
context/e2e_intent.json
ground_truths/e2e_intent.json
context/local_intent.json
ground_truths/local_intent.json
```

These four files will be installed as read-only ExplainBench package resources. Users do not run question-builder and do not supply an artifact directory for intent-only evaluation.

### Effect artifacts are owned by a submission

Effect questions describe the observed behavior of a particular submitted patch. They are therefore model-specific and use the submission ID as a suffix:

```text
context/e2e_effect__{submission_id}.json
ground_truths/e2e_effect__{submission_id}.json
context/local_effect__{submission_id}.json
ground_truths/local_effect__{submission_id}.json
```

In the finished workflow, these files will be generated by:

```bash
explainbench question-builder local ...
explainbench question-builder end2end ...
```

Historical model-specific effect artifacts will not be permanently embedded in the ExplainBench wheel. They belong to their submissions, not to the benchmark-wide package data.

## Temporary effect-artifact workflow

Question-builder functionality is not implemented yet. During evaluation development, existing effect artifacts can be copied from `dataset/context/` and `dataset/ground_truths/` into a workspace that already follows the future question-builder output contract:

```text
question-artifacts/
├── context/
│   ├── e2e_effect__my-agent.json
│   └── local_effect__my-agent.json
└── ground_truths/
    ├── e2e_effect__my-agent.json
    └── local_effect__my-agent.json
```

Example temporary staging commands:

```bash
mkdir -p question-artifacts/context question-artifacts/ground_truths

cp dataset/context/local_effect__my-agent.json \
  question-artifacts/context/
cp dataset/ground_truths/local_effect__my-agent.json \
  question-artifacts/ground_truths/

cp dataset/context/e2e_effect__my-agent.json \
  question-artifacts/context/
cp dataset/ground_truths/e2e_effect__my-agent.json \
  question-artifacts/ground_truths/
```

This staging step is intentionally outside the evaluator. The evaluator consumes the artifact directory but does not care whether it was populated manually or by question-builder. Replacing manual copying with question-builder must not require changes to the evaluation API or CLI.

## Supported question types

Canonical task names:

| Task | Ownership | Context filename | Ground-truth filename |
|---|---|---|---|
| `e2e.intent` | ExplainBench | `e2e_intent.json` | `e2e_intent.json` |
| `local.intent` | ExplainBench | `local_intent.json` | `local_intent.json` |
| `e2e.effect` | Submission | `e2e_effect__{submission_id}.json` | `e2e_effect__{submission_id}.json` |
| `local.effect` | Submission | `local_effect__{submission_id}.json` | `local_effect__{submission_id}.json` |

Every context file has a corresponding file under `ground_truths/`. Context alone is sufficient to generate an answer, but ground truth is required to score it.

## CLI contract

### Lite mode

```bash
explainbench evaluate submission.json \
  --mode lite \
  --output results.json
```

Lite mode resolves to:

```text
e2e.intent
local.intent
```

It requires explanations but does not require patches or an external artifact directory.

### Full mode

```bash
explainbench evaluate submission.json \
  --mode full \
  --artifacts-dir ./question-artifacts \
  --output results.json
```

Full mode resolves to:

```text
e2e.intent
e2e.effect
local.intent
local.effect
```

It requires explanations, nonempty patches, and both model-specific effect artifact pairs.

### Fine-grained task selection

Select one task:

```bash
explainbench evaluate submission.json \
  --task local.intent \
  --output results.json
```

Select multiple tasks:

```bash
explainbench evaluate submission.json \
  --task local.intent \
  --task e2e.effect \
  --artifacts-dir ./question-artifacts \
  --output results.json
```

Rules:

- `--task` is repeatable.
- Supported values are `e2e.intent`, `e2e.effect`, `local.intent`, and `local.effect`.
- `--mode` and `--task` are mutually exclusive.
- The user must select exactly one mode or at least one explicit task.
- `--artifacts-dir` is required whenever an effect task is selected.
- Selecting any effect task requires nonempty `model_patch` values in the submission.

Planned evaluator options:

```text
--model MODEL
--num-generations N
--workers N
--output PATH
--artifacts-dir PATH
```

## Internal task registry

Task selection and artifact behavior will be declared rather than hard-coded throughout the CLI and runner:

```python
@dataclass(frozen=True)
class TaskSpec:
    name: str
    artifact_stem: str
    scope: Literal["e2e", "local"]
    dimension: Literal["intent", "effect"]
    task_class: type[Task]
```

Mode presets:

```python
MODE_TASKS = {
    "lite": (
        "e2e.intent",
        "local.intent",
    ),
    "full": (
        "e2e.intent",
        "e2e.effect",
        "local.intent",
        "local.effect",
    ),
}
```

The task registry will also determine whether package resources or external effect artifacts are required.

## Artifact resolution

### Intent

Intent artifacts are loaded through `importlib.resources` from the installed package:

```text
explainbench package data/context/e2e_intent.json
explainbench package data/context/local_intent.json
explainbench package data/ground_truths/e2e_intent.json
explainbench package data/ground_truths/local_intent.json
```

There is no agent-suffixed intent lookup.

### Effect

For `submission_id = my-agent`, the evaluator resolves:

```text
{artifacts_dir}/context/e2e_effect__my-agent.json
{artifacts_dir}/ground_truths/e2e_effect__my-agent.json
{artifacts_dir}/context/local_effect__my-agent.json
{artifacts_dir}/ground_truths/local_effect__my-agent.json
```

Effect files do not fall back to packaged historical artifacts. Missing required files cause a clear error before any evaluator-model requests are made.

The submission ID must be safe for filename construction. Path separators and traversal components will be rejected.

## Typed artifact validation

Each selected task will have a typed context model. The artifact loader will:

1. Parse the context and ground-truth files.
2. Require top-level JSON objects keyed by instance ID.
3. Validate the fields required by that task's prompt.
4. Verify that context and ground-truth key sets match.
5. Normalize ground-truth answers.

The existing intent ground truths have two answer representations:

```json
{"answer": "d"}
```

and:

```json
{"answer": ["d"]}
```

Both will normalize to `list[str]` internally.

## Evaluation instance selection

For each selected task, instances are joined by `instance_id`:

```text
submitted explanation
  + task context
  + task ground truth
```

The evaluable set is:

```python
submission_ids & context_ids & ground_truth_ids
```

Behavior:

- Context/ground-truth key-set mismatches are invalid artifact errors.
- Submission instances without artifacts for a selected task are reported as skipped.
- Missing instances are never silently discarded.
- A task with no evaluable instances fails before inference.
- A reduced effect artifact set does not prevent other selected tasks from running.

## Evaluation engine

Reusable evaluation code will move behind the installed package API:

```text
src/explainbench/evaluation/
├── __init__.py
├── artifacts.py
├── inference.py
├── registry.py
├── runner.py
├── schemas.py
├── scoring.py
└── tasks.py
```

The public Python API will be approximately:

```python
def evaluate_submission(
    submission: Submission,
    tasks: Sequence[str],
    *,
    model: str,
    num_generations: int,
    workers: int,
    artifacts_dir: Path | None,
) -> EvaluationResult:
    ...
```

The CLI remains a thin adapter around this API.

For each task and instance, the runner will:

1. Build the existing ExplainBench prompt.
2. Insert the submitted explanation and task context.
3. Request structured task-specific output from the evaluator model (an answer list for three tasks, or before/after selections for end-to-end effect).
4. Repeat according to `--num-generations`.
5. Score normalized predictions against normalized ground truth.
6. Record usage, predictions, scores, skips, and failures.

The first implementation performs generation and scoring together. The older `--gen-only` and `--eval-only` options are not part of the initial package CLI.

## Result document

The output is one versioned JSON document containing selection metadata and per-task results:

```json
{
  "schema_version": 1,
  "submission_id": "my-agent",
  "selection": {
    "mode": "lite",
    "tasks": ["e2e.intent", "local.intent"]
  },
  "evaluator": {
    "model": "configured-model",
    "num_generations": 5,
    "token_usage": {
      "completion_tokens": 100,
      "prompt_tokens": 1000,
      "total_tokens": 1100
    }
  },
  "tasks": {
    "e2e.intent": {
      "statistics": {
        "mean": 0.72,
        "sem": 0.03
      },
      "counts": {
        "submitted": 297,
        "evaluated": 297,
        "skipped": 0,
        "failed": 0
      },
      "instances": {
        "astropy__astropy-12907": {
          "predictions": [{"answer": ["d"]}],
          "scores": [1.0]
        }
      },
      "skipped_instance_ids": [],
      "failures": {}
    }
  }
}
```

Statistics will be reported separately for each task. Any overall score will be explicitly defined as a macro-average rather than implicitly mixing task results.
Each task mean is computed across instance-level mean generation scores. SEM is computed across those instance-level means and is `null` when fewer than two instances complete successfully.

## Implementation sequence

### Stage 1: Package shared intent artifacts

- Copy the two intent context files and two intent ground-truth files into package resources.
- Exclude historical effect artifacts and unrelated files such as `raw_pbts.json`.
- Verify all four intent files contain the same 297 instance IDs.
- Test loading the resources from an installed wheel outside the repository.

### Stage 2: Task selection and artifact loading

- Implement the task registry and mode presets.
- Add repeatable fine-grained task selection.
- Implement package-resource loading for intent.
- Implement `--artifacts-dir` loading for effect.
- Add typed artifact schemas and answer normalization.
- Validate safe submission IDs for effect filenames.

### Stage 3: Evaluation engine

- Refactor the existing MCQ schema, prompts, inference wrapper, and scoring into `src/explainbench/evaluation/`.
- Accept the new unified `Submission` object.
- Join submission explanations with selected artifacts by instance ID.
- Preserve parallel inference and generation-count support.
- Record inference failures without discarding completed results.

### Stage 4: CLI and results

- Implement `explainbench evaluate`.
- Add lite, full, and fine-grained selection.
- Add model, generation, worker, artifact-directory, and output options.
- Write the versioned unified result document.
- Ensure missing effect artifacts fail before any paid inference.

### Stage 5: Verification

- Unit-test task resolution and CLI exclusivity.
- Unit-test shared intent and model-specific effect resolution.
- Unit-test artifact validation and answer normalization.
- Test missing and reduced artifact sets.
- Mock evaluator-model calls for deterministic runner and scoring tests.
- Build and install the wheel in an isolated environment.
- Run an installed lite-mode smoke test without repository-relative paths.
- Run a staged-effect smoke test using copied historical artifacts.
